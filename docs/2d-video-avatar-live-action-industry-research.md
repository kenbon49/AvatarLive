# 二维真人数字人直播动作方案与行业调研

> 调研日期：2026-08-28（Asia/Shanghai）
>
> 目的：确认真人视频型数字人是否必须依赖 3D 骨骼，并整理商品介绍动作在行业产品、公开专利和 AvatarLive 中的可落地实现方式。

## 1. 结论先行

对于真人视频型数字人，行业主流并不是要求客户提供 3D 骨骼、3D 人物模型或动作捕捉数据，而是采用：

```text
二维真人动作底板
-> 动作区间标记/动作片段库
-> 直播脚本语义匹配
-> TTS 发音时间轴对齐
-> 身体动作片段切换或拼接
-> 口型驱动
-> 商品卡、PPT、字幕合成
-> 实时推流
```

3D 骨骼、SMPL、OpenPose 和 retargeting 可以作为某些动作迁移或跨人物复用方案的内部实现，但不是 2D 真人数字人的前置输入要求。

上一轮将 3D 动作重定向放在较显眼的位置并不准确。对 AvatarLive 当前路线，更合理的主路径是“2D 动作底板 + 语义动作调度”，而不是先建立 3D 骨骼系统。

## 2. 行业公开方案

### 2.1 百度曦灵：二维底板和动作区间标记

官方资料：

- [2D 小样本数字人（通用口型）拍摄指南](https://xiling.cloud.baidu.com/doc/AI_DH/s/8m0uiiv0m)
- [2D 小样本数字人（专属口型）拍摄指南](https://cloud.baidu.com/doc/AI_DH/s/Km0z4gcpv)

百度文档明确说明，2D 真人数字人的姿态和动作来自上传的视频底板，口型由 AI 重新生成。客户不需要提供 3D 骨骼。

针对交互人像，文档建议拍摄一条连续视频，交替包含：

```text
聆听状态 5-8 秒
-> 播报动作 2-4 秒
-> 聆听状态 5-8 秒
-> 播报动作 2-4 秒
-> ...
```

训练时使用 `dynamicAction` 标记动作区间，例如：

```json
{
  "dynamicAction": [[6, 9], [14, 16], [21, 24], [29, 32]]
}
```

这些区间表示动作的起止秒数，按 25 FPS 处理。百度要求动作开始和结束时手部已经处于稳定状态，头部尽量回到正位，避免在抬手或收手的中间位置截断。

百度还特别提醒：通用 2D 数字人应优先使用摊手、合手、上下叠手等无强语义的小动作，不建议在通用底板中固定使用挥手、摇头、比数字等动作，因为这些动作不一定适合所有文本和场景。

这说明行业上存在两个层次：

1. 通用自然动作：可在多数文本中循环使用。
2. 业务语义动作：需要为特定场景、商品或脚本准备专用素材。

### 2.2 阿里云 DVH：单底板和多底板

官方资料：

- [视频版 2D 数字人形象定制](https://help.aliyun.com/zh/avatar/avatar-application/user-guide/customized-digital-2d-video-avatar/)
- [2D 高精度视频数字人形象定制指南](https://help.aliyun.com/zh/avatar/avatar-application/user-guide/customized-digital-2d-video-guide)

阿里云公开说明：

- 数字人的动作从训练视频中截取；
- 2D 高精度数字人通常选取约 10-15 秒动作片段，并以正放/倒放方式循环；
- 表情、眼神和肢体动作会跟随底板；
- 只有口型部分由 AI 根据新的音频生成；
- 实时对话支持单底板和多底板。

两种底板模式的取舍是：

| 模式 | 动作来源 | 优点 | 限制 |
| --- | --- | --- | --- |
| 单底板 | 聆听和播报使用同一段连续视频 | 连贯、切换自然 | 动作表现较单一 |
| 多底板 | 聆听和播报使用不同视频片段 | 表现力更强 | 底板切换可能产生跳帧 |

阿里云还建议根据应用场景设计真人动作。例如电商直播需要更热情的状态，并使用手势强调产品亮点。这依然是录制动作底板，不是客户提供 3D 骨骼。

### 2.3 腾讯云：2D 小样本和生成式直播

官方资料：

- [腾讯云智能数智人 SDK 接入整体介绍](https://cloud.tencent.cn/document/product/1240/103423)
- [腾讯云智能数智人 2D 端渲染 SDK](https://cloud.tencent.com/document/product/1240/118294)
- [腾讯云 AIGC 直播/数字人直播](https://cloud.tencent.com/document/product/267/126574)

腾讯云的 2D 小样本方案支持通过照片或短视频定制真人数字人，并通过流式音频驱动口型。其 2D 端渲染方案在终端完成数字人和口型渲染，没有要求客户提供 3D 骨骼。

腾讯云的 AIGC 直播是另一条路线：输入主播图片、商品图片、商品简介和话术文本，生成数字人直播视频。官方公开了产品流程，但没有披露详细的动作表示、动作检索或动作调度协议。

因此腾讯云同时体现了两条行业路线：

```text
2D 小样本：视频底板/形象资产 + 口型驱动
AIGC 直播：图片/文本/商品素材 + 生成式视频模型
```

### 2.4 生成式视频路线：不需要外部骨骼，但不是 MuseTalk 增量方案

目前还有一条新路线是直接用图片、音频和文本提示词生成全身视频，不要求客户提供 3D 骨骼：

- Vidu S1：官方宣传支持图片创建角色、语音驱动动作、25 FPS 实时交互和长时间生成。
- Alibaba Live Avatar：使用 14B 扩散模型和块级自回归生成，项目页宣称支持 10,000 秒以上的连续视频。
- Tencent StreamAvatar：输入参考图和音频，生成带说话/聆听反应及全身手势的流式视频。
- OmniAvatar：支持音频驱动、提示词控制动作幅度、情绪以及人物与物体互动。
- Wan-S2V、HunyuanVideo-Avatar：根据图片、音频和提示词生成表情、身体动作或表演视频。

这些方案的共同点是：

```text
用户不提供 3D 骨骼
-> 模型内部从音频、文本和视频先验推断动作
-> 直接生成全身视频
```

但它们已经是大型视频生成模型，和当前 MuseTalk 的定位不同：

- 推理成本更高；
- 直播首帧和持续吞吐要求更高；
- 手部、商品细节和身份一致性仍需验证；
- 动作控制接口通常不如动作片段库透明；
- 若直接接入，需要替换当前身体底片渲染路径，而不是只扩展几个 MuseTalk 动作 ID。

### 2.5 视频动作迁移路线

MimicMotion、LivePortrait 等方案可以使用一段 2D 驱动视频来迁移动作，不要求用户提供 3D 骨骼。模型内部可能提取姿态或运动特征，但外部输入仍然是视频。

这类方案适合：

- 生成新的动作底片；
- 将一个真人的动作迁移到另一个形象；
- 通过动作参考视频批量制作动作素材。

它们更适合离线生成动作资产，暂时不应被理解成直播时针对每条商品话术即时生成完整身体动作。

## 3. 专利与动作实现的对应关系

### 3.1 CN117354584B：最直接的语义动作方案

这件专利最接近“商品文案和动作结合”的问题。其公开流程是：

```text
口播文本
-> 提取与关键动作有关的关键词
-> 根据关键词选择关键动作视频片段
-> 根据文本风格选择风格动作片段
-> 按关键词在文本中的位置拼接动作
-> 生成动作底版视频
-> 对底版视频做唇形驱动
```

专利中举到的动作包括：

- 方向指示动作；
- 数字指示动作；
- 问候动作；
- 模仿物体大小或形状的动作；
- 强调商品优势的动作；
- 鼓掌、招手、加油、佩服等情绪动作；
- 跳跃、踱步、转身等风格动作；
- 多个动作组成的组合动作。

它还提到以下工程细节：

- 建立动作片段库；
- 为动作片段标记 `action_id`；
- 建立关键词和 `action_id` 的映射关系；
- 可以用 JSON、NPY 等格式保存动作数据；
- 用 TTS 获得关键词发音时间戳；
- 根据发音时间对齐动作片段；
- 在动作之间使用基础姿态、过渡姿态或插帧；
- 如果前一个动作过长，可以删除下一个动作，或用风格动作填充；
- 最后使用 Wav2Lip、DINet 等唇形算法生成目标视频。

这件专利并不要求 3D 骨骼作为必需输入。它提到 OpenPose、SMPL 和动作重定向，主要是为了把基准人物动作迁移到其他虚拟人物，是可选的跨人物复用路径。

### 3.2 CN119420954A：直播脚本调度

该专利负责的是内容和节目调度：

```text
原始商品脚本
-> 执行脚本并收集评论
-> 生成实时互动脚本
-> 将互动脚本插入原脚本
-> 回答完成后恢复原脚本位置
-> 依据观看、点击、订单和互动数据优化话术
```

它没有详细规定人体动作如何生成，但实时脚本可以携带动作字段，例如：

```text
text: "这款产品有三大优势"
action: "count_3"
priority: "normal"
```

因此它可以作为动作调度器的上层内容来源。

### 3.3 CN118474404A：商品内容和讲解同步

该专利主要通过向量库，将当前讲解文本匹配到商品图片、PPT、视频或展示页面。

它解决的是：

```text
讲解文本
-> 匹配商品展示内容
-> 同时展示数字人和商品资料
```

它没有详细公开人体动作生成算法，但动作系统可以使用同一个讲解时间轴，让“指向右侧”动作和右侧商品卡同时出现。

### 3.4 其他专利

- CN118101978A：互动输出可包括语音、动作、表情和特效，但未公开动作片段如何生成。
- CN120529145A：根据场景和环境数据生成数字人讲解，偏向场景慢直播，未详细说明商品动作机制。
- CN118075559A：按词组或断句边界进行人工接管、中断和恢复，对动作队列的安全切换有参考价值。

## 4. 商品动作的行业化实现方式

### 4.1 动作类型

可以先从可控、可审核的动作开始：

| 语义 | 动作 ID 示例 | 使用场景 |
| --- | --- | --- |
| 欢迎 | `welcome` | 开场、欢迎观众 |
| 指向左侧 | `point_left` | 指向左侧商品卡或参数 |
| 指向右侧 | `point_right` | 指向右侧商品卡或视频 |
| 数字 1/2/3 | `count_1`、`count_2`、`count_3` | 讲解多个卖点 |
| 展示大小 | `show_size` | 介绍尺寸、容量、空间 |
| 对比 | `compare_left_right` | 比较两个规格或版本 |
| 强调 | `emphasis` | 突出核心参数或优势 |
| 展示/承接 | `present` | 手掌向上展示商品信息 |
| 促销 | `offer` | 优惠、下单、限时活动 |
| 感谢 | `thank` | 结束、感谢、下单后 |

### 4.2 动作素材规范

每个商品动作应当是一个可复用的二维视频片段，并尽量满足：

- 演员闭嘴或嘴部保持中性；
- 动作开始和结束回到统一中性姿态；
- 相机、焦距、灯光、背景和服装保持固定；
- 手势不遮挡嘴、脸和脖子；
- 动作不出画面；
- 记录动作适用方向、时长和目标区域；
- 取得肖像、表演、声音和商业使用授权；
- 对动作做人工审核，避免手部变形、跳帧或不自然过渡。

一个动作清单可以采用如下形式：

```json
{
  "id": "point_right",
  "keywords": ["右侧", "右边", "看右边", "商品图"],
  "mode": "once",
  "start_pose": "neutral",
  "end_pose": "neutral",
  "duration_min": 0.8,
  "duration_max": 1.8,
  "target_anchor": "product_card_right",
  "file": "point_right.npz"
}
```

### 4.3 文案和动作编排

LLM 或规则层不应只返回一段纯文本，应该输出带动作标记的结构化脚本：

```json
{
  "text": "这款产品有三大优势，第一是续航时间长，第二是重量更轻。",
  "segments": [
    {
      "text": "这款产品有三大优势",
      "action": "count_3"
    },
    {
      "text": "第一是续航时间长",
      "action": "count_1"
    },
    {
      "text": "第二是重量更轻",
      "action": "count_2"
    }
  ]
}
```

经过 TTS 字词时间戳后，动作计划可以变成：

```text
0.0-1.1 秒：talk_subtle
1.1-1.9 秒：count_3
1.9-3.3 秒：count_1
3.3-4.7 秒：count_2
4.7 秒以后：talk_subtle
```

如果某段文本没有匹配动作、动作片段过长或多个动作时间冲突，应降级到 `talk_subtle` 或风格动作，不能强行堆叠动作。

### 4.4 商品卡和动作目标绑定

“指向商品卡”要求动作素材和画面布局一致。例如：

```text
商品卡位置：画面右侧
动作：point_right
触发词：右侧、看这里、商品图
```

二维视频动作通常只能指向固定区域。如果商品卡位置动态变化，需要：

- 固定商品卡布局；
- 为左、中、右准备不同动作素材；
- 或使用具备目标锚点的动作重定向系统；
- 或改用生成式视频/3D 驱动路线。

二维动作底板可以很好地实现“指向固定区域、比划大小、数字手势、强调卖点”，但不能天然实现对任意移动商品的真实跟踪或拿取。

## 5. AvatarLive 当前状态和差距

### 5.1 当前 MuseTalk 动作运行时

当前动作白名单位于 [apps/musetalk/action_runtime.py](../apps/musetalk/action_runtime.py)：

```text
idle
talk_subtle
welcome
point
thank
```

当前 `auto` 只做有限关键词匹配：

```text
欢迎、你好       -> welcome
看这里、参数、重点 -> point
感谢、下单、再见 -> thank
其他文本         -> talk_subtle
```

每次播报创建一个动作计划，one-shot 动作结束后回到 `talk_subtle`。当前还没有完整的“单句多动作时间轴”。

### 5.2 当前动态动作生成能力

项目已经有提示词生成动态形象底片的能力，相关逻辑在 [src/lib/avatar-motion.ts](../src/lib/avatar-motion.ts)。生成提示词要求：

- 保持人物身份、服装和构图；
- 根据用户描述改变动作；
- 嘴部基本闭合，因为后续由 MuseTalk 生成口型；
- 生成 loop 或 once 动作。

当前这条路径更适合：

```text
离线生成一个新的动作底片
-> 人工审核
-> 预处理为 MuseTalk profile/NPZ
-> 直播时按固定动作 ID 使用
```

当前并不是直播时为每条商品话术实时生成全身动作。生成任务最后主要形成一个 `talk.mp4` 和一个 `idle.mp4`，还没有形成多个商品语义动作片段组成的动作库。

### 5.3 现阶段缺少的能力

- `point_left`、`point_right`、`count_1`、`count_2`、`show_size` 等商品动作资产；
- 动作片段的关键词、方向、目标区域和时长元数据；
- 一段文本中多个动作的排序和时间轴；
- TTS 字词时间戳与动作开始时间的对齐；
- 动作之间的中性姿态和过渡帧；
- 商品卡位置与动作目标的绑定；
- 互动插入后保存和恢复原商品脚本动作位置；
- 动作冲突时的优先级和安全降级。

## 6. 推荐的 AvatarLive 路线

### 阶段一：扩展 2D 动作资产，不引入 3D 骨骼

优先增加一套经过审核的动作 NPZ 和 manifest 元数据：

```text
welcome
talk_subtle
point_left
point_right
point_up
point_down
count_1
count_2
count_3
show_size
compare_left_right
emphasis
present
offer
thank
```

继续复用 MuseTalk 负责嘴部，身体和手势由动作底片提供。每个动作的首尾都回到中性姿态，以降低切换跳变。

### 阶段二：增加结构化动作编排器

建议在 LLM/TTS 和 MuseTalk 之间增加一层：

```text
商品知识库/直播脚本
-> 文案和 action_id
-> TTS 字词时间戳
-> 动作片段检索
-> 动作时长调整和过渡
-> 身体帧序列
-> MuseTalk 嘴部生成
-> 商品卡/PPT/字幕合成
```

动作解析应使用白名单和置信度，不能直接把 LLM 返回的任意字符串当作文件路径或动作 ID。没有匹配动作时回退到 `talk_subtle`。

### 阶段三：用视频生成模型离线扩展动作库

对于手头没有真人动作素材的新动作，可以使用现有动态动作生成能力、MimicMotion 或其他视频模型提前生成：

```text
动作提示词/动作参考视频
-> 生成闭嘴动作底片
-> 人工质量和身份审核
-> 固定镜头和动作边界检查
-> 预处理为 NPZ
-> 登记 action_id 和关键词
```

直播时只播放已审核的动作片段，不在每条评论到达时临时调用视频生成模型。

### 阶段四：必要时再评估生成式实时渲染

只有在以下需求无法通过动作库满足时，才考虑 Vidu S1、Live Avatar、StreamAvatar、OmniAvatar 等生成式实时渲染路线：

- 任意提示词生成全身动作；
- 动作需要跟随动态商品目标；
- 需要拿取、旋转或操作商品；
- 需要连续生成此前没有录制过的表演动作。

这会成为新的渲染架构，需要单独评估模型吞吐、首帧延迟、显存、身份一致性、手部质量、流式缓存和长时间稳定性，不能视为对 MuseTalk 动作白名单的小改动。

## 7. 最终判断

行业已经证明，不依赖客户提供 3D 骨骼也可以实现真人数字人直播动作，主要方式是：

```text
二维真人动作视频
-> 动作区间切分
-> 动作标签和关键词映射
-> 商品脚本语义调度
-> TTS 时间轴对齐
-> 动作片段切换/拼接
-> MuseTalk 或其他口型模型处理嘴部
```

对于 AvatarLive，最稳妥的产品路线是：

> 先建设“商品语义动作片段库 + 结构化脚本 + TTS 时间轴 + MuseTalk 口型”的 2D 方案，不要求用户提供 3D 建模数据，也不立即替换 MuseTalk。

真正的自由动作生成可以作为离线动作资产生产工具；只有当固定动作库无法覆盖商品互动需求时，才把生成式全身视频模型作为独立渲染路线评估。
